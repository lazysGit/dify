# 部门测试用户体系设计

**日期**: 2026-09-14
**状态**: 待实现
**范围**: 本地开发环境。通过真实控制台页面录入一套可登录、可切角色的部门测试数据，并留下可重复执行的浏览器操作脚本。

**依赖**: `docs/dm/dify-department-web-design.md`、`docs/dm/dify-department-access-control-design.md`

---

## 1. 目标

在本地**现有租户**中准备一套权限矩阵全覆盖的测试用户体系，用来手测和浏览器测部门管理、成员管理、数据隔离、探索发布。

交付物：

1. `dev/seed-department-test-users`：用浏览器操作 `http://localhost:3000` 控制台页面录入数据，不直写数据库、不调用 Flask Service、不绕过前端。
2. 脚本结束后打印账号表。本文档中的账号矩阵是固定契约。

成功标准：owner 在控制台里能看到约定部门树；下表账号（若知识库操作员角色在 UI 中可用则含该账号，否则 10 个）可用密码 `QaTest1234` 登录；`[QA]` 应用和知识库落在约定部门；跨部门发布记录可在探索/发布面板看到。

---

## 2. 非目标

- 不新建租户，不改现有 owner 的邮箱、密码、角色、所属部门。
- 种数过程不切换登录账号，全程用当前已登录的 owner。
- 不灌知识库文档，不配置 LLM。对话能否跑取决于本地是否已配模型。
- 不把该脚本做成产品 Flask CLI。
- 不为这套数据写 pytest / Vitest。
- 不提交任何密钥或运行时 ID 到仓库。

---

## 3. 组织树

复用租户已有默认部门（`is_default`，不能有子部门）。脚本只创建下面四个部门：

```text
默认部门                    （已有则复用，不改名、不删除）
研发部                      （根部门）
  └── 前端组                （研发部子部门）
市场部                      （根部门）
法务部                      （根部门；无成员、无部门管理员、无应用、无知识库）
```

创建顺序：研发部 → 市场部 → 法务部 → 前端组（父部门选研发部）。

幂等键：同租户下可见部门名。已存在则复用，不重复创建。

## 5. 应用与知识库

名称一律带 `[QA]` 前缀。`--reset` 只删该前缀对象。

当前空白创建应用弹窗、空白创建知识库弹窗**不会**在创建时选择部门，资源会落到 owner 当前部门。因此归属部门用卡片菜单「转移部门」完成，不伪造 `department_id`。

### 5.1 应用

应用类型：聊天助手（`chat`）。不填复杂编排。

| 名称 | 目标部门 | 发布到 | 测什么 |
|------|----------|--------|--------|
| `[QA] 研发内部助手` | 研发部 | 研发部 | 本部门可见，市场部看不见 |
| `[QA] 前端组件助手` | 前端组 | 前端组 | 子部门应用；研发部管理员能看到，市场部不能 |
| `[QA] 市场文案助手` | 市场部 | 市场部 | 兄弟部门隔离 |
| `[QA] 默认部门应用` | 默认部门 | 默认部门 | 滞留默认部门的数据 |
| `[QA] 跨部门投放` | 研发部 | 市场部 | 探索过滤：市场成员能看到发布结果 |

每个应用的页面步骤：工作室创建聊天应用 → 回到应用列表 → 卡片菜单转移部门（若已在目标部门则跳过）→ 进入应用概览 → 设置发布部门。

若 owner 当前就在默认部门，`[QA] 默认部门应用` 无需转移。

幂等键：应用列表中的精确名称。已存在则只补做缺失的转移和发布，不重建。

### 5.2 知识库

只建空知识库，不上传文档。

| 名称 | 目标部门 | 测什么 |
|------|----------|--------|
| `[QA] 研发知识库` | 研发部 | 本部门知识库隔离 |
| `[QA] 前端知识库` | 前端组 | 子部门知识库；研发部管理员可见 |
| `[QA] 市场知识库` | 市场部 | 兄弟部门不可见 |
| `[QA] 默认知识库` | 默认部门 | 默认部门滞留数据 |

每个知识库的页面步骤：知识库页创建空知识库 → 回到列表 → 卡片菜单转移部门（若已在目标部门则跳过）。

法务部不放应用和知识库。

幂等键：知识库列表中的精确名称。

## 6. 脚本

### 6.1 入口

```bash
dev/seed-department-test-users              # 幂等录入
dev/seed-department-test-users --reset      # 先按页面删除这批数据，再重建
dev/seed-department-test-users --dry-run    # 只打印步骤，不操作浏览器
```

实现放在 `dev/`。用本机 Chrome（browser-use / Cursor 浏览器工具）驱动页面。请求必须由页面上的按钮和表单发出。

控制台地址：`http://localhost:3000`。

### 6.2 前置条件

1. 本地 API 与前端已启动。
2. Chrome 中 owner 已登录目标工作空间。
3. 未登录、停在登录页、或当前账号不是 owner：脚本停止，提示先用 owner 登录。不代替用户输入密码。

租户选择：使用当前浏览器会话里的工作空间。不扫描数据库、不接受 `--tenant-id`。

### 6.3 录入顺序

1. 打开设置 → 部门，按第 3 节创建部门。
2. 打开设置 → 成员，按第 4 节创建账号。
3. 打开工作室，按第 5.1 节创建、转移、发布应用。
4. 打开知识库，按第 5.2 节创建、转移知识库。
5. 在终端打印账号表（显示名、邮箱、密码、角色、部门、是否部门管理员）。运行时 ID 只打终端，不写仓库。

任一步失败：停止，打印已完成项和失败步骤，不自动回滚（可用 `--reset` 再跑）。

### 6.4 `--reset`

只通过页面删除，且只删这批测试数据：

1. 删除名称以 `[QA]` 开头的应用。
2. 删除名称以 `[QA]` 开头的知识库。
3. 从工作空间移出邮箱为 `@dify.test` 的成员。
4. 按叶子到根删除部门：前端组 → 法务部 → 市场部 → 研发部。

不删除默认部门，不操作现有 owner，不删除名称不含 `[QA]` 的应用/知识库，不移出非 `@dify.test` 成员。

若页面因「部门仍有成员/应用/知识库」拒绝删除，视为 `--reset` 失败，停止并说明残留对象。

### 6.5 幂等（无 `--reset`）

按页面可见名称/邮箱判断。已存在则跳过创建，继续后续补齐（例如应用已在、发布部门未设则只补发布）。

| `qa-dept-default-normal@dify.test` | 只看见默认部门数据 |
| `qa-dept-rd-dataset@dify.test` | 不能创建应用；能看见本部门知识库 |

## 8. 风险与约束

- 选择器依赖中文/当前 i18n 文案和弹窗结构，前端改版后脚本要跟着改。
- 创建 11 个成员 + 5 个应用 + 4 个知识库步骤多，任一步超时或 toast 失败即停。
- 成员创建会入队欢迎邮件；Celery 未启动不阻断页面成功。
- 本地未配模型时应用可以创建，但不能对话。这不视为脚本失败。
